# Progress Update — 2026-09-12 22:15

## Bug: duplicate turns / "freeze" when toggling Developer Mode

User reported the UI "freezes" and the active question gets "distorted" (duplicated) when
toggling Developer Mode -- screenshot showed the same user message appearing 3 times in a row,
each with a distinct, real assistant response.

**Root cause (confirmed by tracing, not guessed):** real LLM calls are slow (session telemetry
showed ~125s total across 7 calls, i.e. many seconds each, worse for the new "complex" tier
routing which can chain 3+ sequential calls). Streamlit runs a session's script synchronously,
single-threaded -- a long turn makes the whole page LOOK frozen. If the user resubmits the same
text (or clicks a sample/follow-up button) during that window, Streamlit doesn't drop it: it
queues the new widget value and runs it as a genuinely separate, valid submission once the
first run finishes -- producing exactly the observed duplicate turns with identical text. This
wasn't specific to the dev-mode toggle itself (confirmed toggling alone, with no resubmission,
does not duplicate anything); the toggle just coincided with the user's frustrated retry during
a slow call.

**Fix:** `ui/app.py` now disables `chat_input` and every button (sample questions, follow-ups,
reset) for the full duration of a turn, via a two-run pattern that's the standard Streamlit
idiom for this exact problem (a single run can't both render "disabled" to the browser AND
immediately follow with blocking work in a way the browser sees before that work finishes --
the disabled state has to already be flushed on a PRIOR run):
- Run A (new input detected): sets `processing=True`, stashes the message, calls `st.rerun()`
  immediately -- does zero slow work itself.
- Run B (triggered by Run A's rerun): `processing` is already `True` at the top, so
  `chat_input(disabled=True)` renders and flushes to the browser *before* the slow
  `_process_turn()` call happens later in that same run. The browser has the input visibly
  disabled for the entire duration of the blocking call, so a resubmission attempt can't even
  be sent, let alone queued.
- After the turn finishes, `processing=False` + one more `st.rerun()` re-enables everything.

**Verification:** `AppTest` (Streamlit's own headless test harness) resolves chained
`st.rerun()` calls automatically within one `.run()`, so it can't directly show the transient
"disabled, still computing" frame -- traced the run-by-run logic by hand instead to confirm the
invariant holds by construction. Ran three consecutive turns through three different input
paths (chat_input, a sample-question button, a follow-up button) with dev mode toggled on
in between, and confirmed history grows by exactly 2 per turn (2 → 4 → 6, then 0 after reset)
with zero duplication anywhere. 24/24 offline tests still pass.
