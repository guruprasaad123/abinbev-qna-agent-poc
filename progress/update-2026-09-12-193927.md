# Progress Update — 2026-09-12 19:39

## Streamlit developer-mode UI (new)

Built `ui/app.py` — a Streamlit chat interface with a "Developer mode" sidebar toggle that
shows a live, step-by-step trace of the orchestrator's actual workflow for the turn being
answered right now: intent/entity resolution (including auto-corrected abbreviations/aliases/
typos), routing to sub-agents, each sub-agent's tool usage and evidence, and synthesis
(including whether a validation retry fired).

**Streamlit vs Gradio decision** (quantitative comparison requested): logged to
`progress/streamlit-vs-gradio-2026-09-12-190520.md`. Streamlit chosen — comparable GitHub
stars (~44-45K both), ~2x Gradio's PyPI downloads, and critically, `AgentResponse` is a rich
structured object (SQL used, citations, markdown table, raw NLU JSON, retry flag) that maps
better onto Streamlit's general-purpose widgets (`st.dataframe`/`st.json`/`st.code`) than onto
Gradio's per-message chat-metadata accordion, even though that accordion is a more purpose-built
fit for a pure tool-call log.

**Implementation:**
- `src/orchestrator.py::handle_turn` gained an optional `on_step(phase, detail)` callback
  (default `None`, zero behavior change for every other caller -- CLI, notebook, tests), fired
  live at each milestone: `nlu`, `routing`, `subagent` (once per sub-agent invoked), `synthesis`
  (start/retry/done).
- Added `_detect_corrections(user_message, entities)`: flags a canonical entity (zone/country/
  brand/kpi) that doesn't appear verbatim in the raw user message as likely auto-corrected from
  an abbreviation/alias/typo -- this is what surfaces "NA rev" -> "North America" / "Revenue" in
  the dev-mode trace.
- `pyproject.toml`/`requirements.txt`/`uv.lock` gained `streamlit` as an optional `ui` extra.

**Verification:** no `chromium-cli`, no Python/Node Playwright available in this environment
(Node here is v12, too old for modern Playwright), so verification was two-layered instead of a
screenshot: (1) `streamlit run ui/app.py` boots cleanly, HTTP 200, `_stcore/health` returns `ok`,
zero errors in the server log; (2) drove the exact `handle_turn(msg, on_step=...)` call the UI
uses, live against the real configured gateway, for both a normal question and an abbreviation
question -- confirmed all 4 trace phases fire in order with real data, and the correction
detector correctly flagged `zone -> North America` and `kpi -> Revenue` for "NA rev Q1 2024?".

## Model routing: smarter-but-quota-limited model, spent on one role only

User's free-tier gateway (tokenharbor.ai) offers `deepseek-v4.1-flash:free` (higher benchmark
intelligence, 39.5, but rate/quota-"LIMITED") alongside the regular `deepseek-v4-flash:free`
(35.0, unlimited), and a third, much weaker `mimo-v2.5:free` (22.3, multimodal).

**Decision:** put the limited smarter model on `LLM_MODEL_SYNTHESIZE` only, not `CLASSIFY`/
`GENERATE`. Reasoning: `classify` fires on every single turn (including greetings) and only
needs reliable schema-following; `synthesize` is the one role the codebase's own docs already
call "the one tier worth paying for a stronger model" -- judgment on assumptions/limitations,
multilingual fluency, avoiding hallucination. `.env`'s `LLM_MODEL_SYNTHESIZE` updated to
`deepseek-v4.1-flash:free`.

**`mimo-v2.5:free` -- not used anywhere.** Its differentiator (multimodality) is irrelevant --
nothing in this pipeline touches images/audio/video. Its text-only intelligence (22.3) is well
below `v4-flash` (35.0), which already caused two real bugs this session (JSON-array-wrapping,
truncated/leaked reasoning) -- dropping further, especially for `classify`'s nested-JSON schema
or `generate`'s SQL-safety-constrained output, was judged too risky to use without dedicated
testing, and there's no upside to offset that risk here.

**Rate-limit fallback (new code, not just config):** flagged a real risk before switching --
`src/llm_client.py` had no rate-limit handling at all, so a "LIMITED" model hitting its quota
mid-session would crash the turn with an unhandled exception, the same failure class already
hardened against for token-truncation. Fixed: `AnthropicLLMClient`/`OpenAILLMClient.__init__`
now accept an optional `fallback_model`; `generate()` catches `RateLimitError` on the primary
model and retries once against the fallback instead of raising. `get_llm_client()` wires this
automatically -- the `synthesize` role's fallback is whatever `generate` is configured to use
(the always-available baseline); `classify`/`generate` have no fallback (already the baseline).
Usage/cost is recorded against whichever model actually served the request.

Verified via a mocked test (`RateLimitError` forced on the primary model call) rather than a
real API test, to avoid burning the user's actual limited quota: confirmed it retries against
the fallback model and records usage correctly against it. Then re-ran a real end-to-end query
against the live gateway to confirm the `.env` change took effect -- `orchestrator_synthesis`
correctly used `deepseek-v4.1-flash:free` while `classify`/`generate` stayed on `v4-flash:free`;
v4.1 was not actually rate-limited during this run, so the fallback path itself was not
exercised against the real gateway, only against the mock.

Docs updated: `docs/COST_LATENCY_TRADEOFFS.md` §2 gained a new "Worked example" subsection
covering the placement reasoning and the fallback guard; `src/llm_client.py`'s module docstring
documents the fallback-wiring contract.

18/18 offline tests pass after all of the above.
