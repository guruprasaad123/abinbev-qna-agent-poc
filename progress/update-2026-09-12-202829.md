# Progress Update — 2026-09-12 20:28

## Robustness fix: LLM-provider outages no longer crash a turn

User hit a real crash live in the UI: the free-tier gateway account got blocked
(`402 confidence_level_required`), and the raw Python traceback propagated all the way up
through `Orchestrator.handle_turn` and crashed the Streamlit app -- a direct violation of
required capability #25 ("graceful handling of unsupported or unavailable requests").

Root cause and fix, at the correct layer (not just papered over in the UI):
- `src/llm_client.py`: the rate-limit-only fallback trigger from earlier this session was too
  narrow (only caught `RateLimitError`, not the 402 we actually hit). Broadened to catch any
  provider-SDK `APIError` for the fallback attempt; added `LLMUnavailableError`, one clean,
  provider-agnostic exception the client raises if the primary AND fallback (or no fallback
  configured) both fail, instead of leaking a raw SDK exception.
- `src/orchestrator.py`: `handle_turn` is now a thin wrapper (`_handle_turn_inner` holds the
  real logic) that catches `LLMUnavailableError` and returns a plain, honest degraded
  `AgentResponse` (`unavailable=True`) instead of raising. A separate, narrower guard around
  the best-effort memory-summarization call specifically avoids discarding an
  already-successfully-synthesized answer just because that unrelated call fails afterward.
- Verified two ways: (1) forced every underlying API call to fail with the exact same 402
  error via a mocked client, confirmed `handle_turn` returns cleanly with `unavailable=True`
  instead of raising; (2) the gateway actually recovered on its own mid-session, giving a real
  live answer, confirming the fix doesn't interfere with the normal path.
- `docs/CAPABILITY_MAPPING.md` #25 and `docs/COST_LATENCY_TRADEOFFS.md` §2 updated to document
  this. 18/18 original tests still pass.

## New: dynamic per-turn model routing by query complexity

User upgraded their gateway account to a paid "Agent Pass" (screenshot shared), unlocking
several additional models (GLM-5.3 Flash, Qwen3.8 Flash, GPT-5.6 Luna, MiMo V2.5 Pro) at
usage-based billing rather than the earlier free-tier quota constraint. Asked whether the
system could route dynamically across these based on per-query complexity rather than one
static model per role.

**Research first** (real Artificial Analysis Intelligence Index rankings, not guessed):
GLM-5.3-Flash ~42-46 (best available, and notably cost-efficient per task), GPT-5.6 Luna ~43
(similar quality, pricier), DeepSeek V4.1 Flash 39.5 (already integrated), DeepSeek V4 Flash
35.0 (baseline), MiMo V2.5 Pro ~26. Confirmed the exact gateway model-id string (`glm-5.3-flash`,
not `z-ai/glm-5.3-flash` or other guesses) by testing candidates directly against the API.

**Implementation:**
- `Orchestrator._classify_complexity(nlu, needed_subagents, is_retry=False)`: pure, deterministic,
  **zero extra LLM calls** -- reuses signals already available after NLU + routing (sub-agent
  count, comparison intent, multi-zone/multi-KPI questions, whether a validation retry already
  fired -- which always escalates to `complex`, since retrying the same tier that just
  hallucinated is a worse bet than a stronger one). Unit tested
  (`tests/test_pipeline.py::TestSynthesisComplexityRouting`, 6 new tests, no network needed).
- `src/llm_client.py::get_synthesis_tier_models()`: reads `LLM_MODEL_SYNTHESIZE_SIMPLE` /
  `LLM_MODEL_SYNTHESIZE` (moderate, unchanged name -- existing configs keep working) /
  `LLM_MODEL_SYNTHESIZE_COMPLEX`, with sensible per-provider defaults if unset.
- `LLMClient.generate()` (all 3 implementations) gained an optional `model_override` param --
  the existing, already-constructed `llm_synthesize` client is reused per turn with a
  per-call model override, rather than constructing a new client per complexity tier; the
  client's existing rate-limit/outage fallback (above) still applies underneath whichever tier
  is requested.
- `.env`: `LLM_MODEL_SYNTHESIZE_SIMPLE=deepseek-v4-flash:free`,
  `LLM_MODEL_SYNTHESIZE_COMPLEX=glm-5.3-flash` (moderate unchanged at `deepseek-v4.1-flash:free`).
- `ui/app.py`: dev-mode trace and the persistent "Validation & Guardrails" tab now show which
  complexity tier was chosen and which model was requested for it, including on an escalated
  retry -- verified structurally sound via a mock-backed `AppTest` pass after the change.

**Verified live against the real (now-paid) gateway**, three real end-to-end turns:
- Single-zone/single-KPI question → routed to `deepseek-v4-flash:free` (simple)
- Two-zone comparison → routed to `deepseek-v4.1-flash:free` (moderate)
- 3-sub-agent hybrid question (structured + web + coding) → routed to `glm-5.3-flash`
  (complex), including on its validation retry (which fired for this one)

24/24 offline tests pass (18 original + 6 new). `docs/COST_LATENCY_TRADEOFFS.md` §2 gained a
full subsection on this ("Going further: dynamic per-turn routing *within* the synthesize
role").
