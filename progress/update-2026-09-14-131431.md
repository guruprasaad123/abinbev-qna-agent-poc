# Progress Update — 2026-09-14 13:14

## New: 185-case real-LLM capability test suite, one file per required attribute

User asked for 30-40 realistic test cases per required capability (all 25 from the assignment
brief), organized folderwise under `notebooks/`, plus corresponding coverage in `tests/`. Scaled
down via discussion to ~8-10 cases/capability (185 total) after flagging that 30-40 x 25 would
mean ~750-1000 real LLM calls -- likely many hours and, while cheap per-call, still a lot of
unnecessary volume for a prototype submission. Also confirmed `tests/` should be genuinely
live/real-LLM (not mock), a deliberate architecture addition alongside (not replacing)
`tests/test_pipeline.py`.

**Structure built:**
- `tests/live/runner.py`: `Case`/`CaseRun`/`run_case()` + a library of reusable assertion
  helpers (`intent_is`, `used_subagent`, `citations_nonempty`, `active_filter_contains`,
  `clarification_asked`, etc.) so each of the 185 cases stays a short, readable declaration.
- `tests/live/cases/cap01_*.py` .. `cap25_*.py`: one file per required capability (185 cases
  total, verified by direct import/count), each with realistic questions grounded in the real
  AB InBev dataset (actual zones/KPIs/periods/brands/competitors).
- `tests/live/live_capabilities_suite.py`: turns every case into a real `unittest` assertion.
  Deliberately named to NOT match unittest's default `test*.py` discovery pattern -- this
  prevents a nasty surprise where someone configures a real API key and then runs the normal,
  documented "fast and free" `python3 -m unittest discover -s tests` command, only to
  accidentally trigger an hours-long, real-cost run. Confirmed: top-level discovery is still
  exactly 24 tests (unaffected); the live suite only runs via explicit invocation.
- `scripts/run_live_capability_tests.py`: friendlier CLI with live progress output, `--capability`/
  `--case` filters, and a JSON report per run (pass/fail, real answers, cost, latency).
- `scripts/build_capability_notebooks.py`: renders `notebooks/capabilities/<NN>_<slug>/demo.ipynb`
  directly from an already-completed JSON report -- deliberately does NOT re-run cases live a
  second time (the report already captured real output), avoiding doubling the real-API cost/time
  just to produce the notebook artifact.

**Also fixed while here:** the long-standing `$0.0000` cost-display gap -- `PRICING_PER_MTOK_USD`
in `src/llm_client.py` didn't recognize any of the actually-configured gateway model strings
(`deepseek-v4-flash`, `deepseek-v4.1-flash`, `glm-5.3-flash`), silently falling back to the
`mock` $0/$0 bucket. Added real, current (Sept 2026) published per-token rates for all three,
sourced live (not guessed) -- see `docs/COST_LATENCY_TRADEOFFS.md` §3 for sources. Confirmed
live: a real turn now shows non-zero cost (`$0.000872` for a 3-call turn, previously `$0.0000`).

**Execution status at the time of this log entry:** all 25 capabilities' live runs launched as
background jobs (one per capability, ~7-10 cases each). One real operational hiccup along the
way, worth recording: an initial batch was launched by manually backgrounding OS processes with
`&` inside one shell command -- these got silently orphaned/killed once that shell's tool-call
"completed" (each Bash tool invocation appears to run in its own transient shell, so children
backgrounded with bare `&` don't reliably survive across tool calls). A subsequent `kill -0`
poll loop meant to detect completion had a bug and falsely reported them as finished (empty
report files, no crash evidence) when they were, in fact, silently dead. Relaunched everything
properly via the harness's own `run_in_background: true` per-command tracking instead (one Bash
tool call per capability), which is the reliable mechanism; the stale duplicate first-attempt
processes were found still alive under their original PIDs and killed before they could race
against the correct run and corrupt the shared report files. Results not yet collected as of
this entry -- to be logged in a follow-up entry once all 25 complete.

24/24 offline tests (`tests/test_pipeline.py`) still pass throughout, unaffected.
