# Progress Update — 2026-09-14 13:25

## Real infrastructure event mid-run: free-tier allowance exhausted, switched to paid models

Running 25 capabilities concurrently against the gateway's free-tier models
(`deepseek-v4-flash:free`, `deepseek-v4.1-flash:free`) burned through the account's rolling
7-day free allowance partway through -- a real, confirmed event, not a code bug:

```
429 free_tier_limit_reached: "You've used this period's free allowance. Your next rolling
7-day period starts at 2026-09-18T12:08:27Z. Use the paid model 'deepseek-v4-flash' to keep
going..."
```

Every subsequent turn's `_run_nlu()` call (the `classify` role, which has no fallback of its
own -- see `docs/COST_LATENCY_TRADEOFFS.md` §2) hit this and correctly degraded gracefully
(`AgentResponse.unavailable=True`, per this session's earlier fix) rather than crashing --
which is exactly the intended behavior, but it meant ~18 of the 25 in-flight capability runs
partially or fully failed with `unavailable=True`, not genuine agent defects.

**Root cause confirmed independently** via a direct healthcheck call before touching anything
further. **Fix**: the error message itself named the way out -- non-`:free` PAID variants of
the same models exist and bill against the account's paid balance instead
(`deepseek-v4-flash`, `deepseek-v4.1-flash`, confirmed working via a direct test call before
switching `.env`). Updated `LLM_MODEL_CLASSIFY`/`LLM_MODEL_GENERATE`/`LLM_MODEL_SYNTHESIZE`/
`LLM_MODEL_SYNTHESIZE_SIMPLE` to the paid variants (complex tier was already on the genuinely-
paid `glm-5.3-flash`, unaffected throughout). Verified a real end-to-end turn works cleanly on
the new config before resuming.

**Cleanup**: killed all in-flight background processes immediately upon confirming the root
cause (`pkill -f run_live_capability_tests.py`), then precisely identified which of the 25
capability reports were contaminated by scanning each report's captured answers for the
graceful-degradation message text (not just "did the process exit non-zero," since a
capability can legitimately fail 1 case out of several on its own merits and still be a clean,
trustworthy run) --
- **Clean, keep as-is**: 2, 3, 4, 9, 18, 22 (6 capabilities -- these completed before the quota
  ran out, verified no `unavailable` answers among their cases)
- **Contaminated, needed a clean re-run**: 1, 5, 6, 7, 8, 10, 11, 12, 13, 14, 15, 17, 19, 20,
  21, 23, 24, 25 (18 capabilities)
- **Never got to run at all**: 16 (1 capability)

All 19 affected capabilities relaunched on the paid models as of this log entry; results not
yet collected.
